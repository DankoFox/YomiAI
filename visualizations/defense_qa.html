Why does Pipeline A consistently outperform Pipeline B (HR@10 0.9047 vs 0.7745)? Does that mean DIF-SASRec adds no value?
Architecture
▼
Answer

The two pipelines serve different signals. Pipeline A uses a Cleora co-purchase graph built from millions of actual purchase pairs — its nearest-neighbours encode strong real-world buying patterns. When a user's profile vector lands near a cluster of frequently co-purchased items, the ground-truth next item is very likely in that cluster.

Pipeline B models sequential intent — what the user is trending toward based on click order. It adds most value for users whose recent interest has shifted away from their historical mean: the Cleora pool is anchored in long-term co-purchase affinity, while DIF-SASRec can pivot on a single new click.

In the deployed system both columns are displayed side-by-side, so the comparison is not zero-sum — each answers a different question: "People also buy" vs. "You might like next."

Why a pool of 8 DIF-SASRec agents instead of a single shared model?
Architecture
▼
Answer

Each agent carries its own per-user checkpoint. A shared model would require locking during both the forward pass (scoring) and the backward pass (online fine-tuning), serialising all recommendation requests.

With 8 isolated agents, up to 8 requests run concurrently without contention. The pool size was chosen to saturate the GPU at the target request rate without exceeding the VRAM budget:

3
Why FastAPI + asyncio rather than a synchronous Flask server?
Architecture
▼
Answer

The recommendation route fires two concurrent I/O calls — FAISS HNSW search and Cleora index lookup — plus optional Redis and MongoDB reads. In a synchronous Flask server each request holds a thread for the entire duration, so 50 concurrent users would require 50 threads (~1 MB stack each).

FastAPI's asyncio event loop suspends the coroutine during I/O and serves other requests in the gap, keeping thread count constant. The encoder calls (BGE-M3, CLIP) are CPU/GPU-bound and are explicitly offloaded to a ThreadPoolExecutor via anyio.to_thread.run_sync — they do not block the event loop.

Why MongoDB for interaction logs instead of PostgreSQL?
Architecture
▼
Answer

Interaction logs are append-only, variable-length click sequences with no cross-collection joins. MongoDB's document model stores a user's full click history as a nested array in a single document — reading a user profile is a single findOne with no joins.

PostgreSQL would require a separate interactions table and a GROUP BY user_id join on every profile read. The schema-free format also avoids migrations when the interaction payload schema evolves (e.g., adding a not_interested signal).

5
Why Redis as an interaction write queue rather than writing directly to MongoDB?
Architecture
▼
Answer

The POST /interact endpoint is on the hot path — every click fires it. A direct MongoDB write involves a network round-trip and disk flush that adds 20–30 ms. Redis RPUSH is an in-memory append that completes in under 1 ms, keeping P50 interaction latency at 4 ms for not-interested events.

A background worker drains the Redis queue asynchronously and commits to MongoDB in batches. The only downside is that if the server crashes between a push and the drain, that interaction log is lost — acceptable for a recommendation system where occasional data loss does not break correctness.

6
Why DIF-SASRec over GRU (GRU-SeqDQN)?
AI / ML 🔥 Very likely
▼
Answer

GRU-SeqDQN failed for two structural reasons at 3M-item scale:

1. Intractable action space. The DQN must output a Q-value for all 3 million items at every step. This is computationally intractable and prevents the gradient signal from concentrating on meaningful actions.

2. GRU bottleneck. A single hidden state must compress the entire interaction history into one fixed-size vector, losing positional and temporal context for long sequences.

DIF-SASRec avoids both: the action space is replaced by a dot-product ranking over a pre-filtered 200-item candidate set, and self-attention retains direct positional access to every item in the history window without a bottleneck.

Ablation confirms this: GRU-SeqDQN scored HR@10 = 0.0823 — below random (0.1000) — while DIF-SASRec reaches HR@10 = 0.7745.
7
Why DIF-SASRec specifically rather than plain SASRec or BERT4Rec?
AI / ML 🔥 Very likely
▼
Answer

vs. plain SASRec: SASRec uses a single attention stream over item IDs, discarding semantic content (BGE-M3 embeddings) and categorical structure. DIF-SASRec adds a decoupled second stream over category IDs, fused by a learnable scalar α. This is the direct reason DIF-SASRec can exploit BGE-M3 embeddings already computed for search — no additional encoder is needed.

vs. BERT4Rec: BERT4Rec is bidirectional — it masks items in the middle of the sequence and predicts them from both directions. This produces better representations but makes it incompatible with online fine-tuning. At inference, the model must generate T+1 given 1…T causally. Adding a new click and running a backward pass on a bidirectional model would require re-masking the entire sequence, invalidating cached representations.

SASRec and DIF-SASRec use causal masking, so appending one item adds one new attention row — the gradient step is local and cheap.

9
Why Cleora for the co-purchase graph rather than LightGCN or GraphSAGE?
AI / ML
▼
Answer

LightGCN and GraphSAGE require iterative neighbourhood aggregation over the full graph at training time. For 375k nodes and millions of edges, one epoch of LightGCN takes hours on a GPU and requires memory proportional to neighbourhood depth.

Cleora uses a different approach: it approximates infinite Markov random walks on the bipartite user–item graph via iterated matrix products, converging in 3–5 iterations to stable item co-occurrence embeddings without ever loading the full adjacency matrix into GPU memory.

On the same hardware, Cleora converges in minutes rather than hours. The tradeoff is that Cleora does not produce user embeddings — only item co-purchase embeddings — but the system only needs item-side behavioural signal for Pipeline A, so this is not a gap.

Explain the content veto threshold τ = 0.3. Why 0.3 specifically?

Answer

The veto discards candidates whose cosine similarity to the user's BGE-M3 profile vector is below τ. The sensitivity analysis on a 10k-user sample:

Below 0.3: semantically irrelevant candidates dilute the ranked list without helping recall.

What is the learnable fusion scalar α in your DIF-SASRec implementation, and why initialise at 0.7?
AI / ML
▼
Answer

The standard DIF-SASRec formulation adds content and category attention outputs with a fixed 50/50 weight. The implementation extends this with a sigmoid-gated scalar α learned jointly during pretraining, so the model can decide how much to weight content vs. category per-domain.

Why α₀ = 0.7 (favouring category)? Amazon Books categories (fiction/sci-fi/fantasy) are dense, consistent taxonomic labels that provide strong coarse-grained signal in early training. The content stream (BGE-M3 1024-d) is high-dimensional and takes more gradient steps to converge. Starting category-biased prevents the content stream from dominating before it has been sufficiently trained. After 30 epochs, the scalar is free to settle at whatever α minimises training loss.

14
Why is leave-one-out with N=99 negatives the right evaluation protocol?
Evaluation
▼
Answer

Leave-one-out holds out each user's last interaction as the positive and evaluates whether it appears in the top-k ranked against 99 uniformly sampled negatives. This protocol is standard in sequential recommendation literature (SASRec, BERT4Rec papers use the same).

Using the full catalogue (3M negatives) would make HR@10 degenerate toward 0 for all models — the probability of ranking the ground truth in the top 10 of 3M is near zero without perfect ranking. The N=99 protocol isolates the model's discriminative ability: can it distinguish the true next item from 99 random items? This is more interpretable and directly comparable to published baselines.

Pipeline A ablation shows HR@10 = 0.7626 but the canonical result is 0.9047. That is a 0.14 gap — is that suspicious?
Evaluation 🔥 Very likely
▼
Answer

This is a known artefact of the 99-negative protocol interacting with Pipeline A's scoring function — not a methodological flaw.

Pipeline A assigns a score of -2.0 to any candidate outside the Cleora ASIN set (375k items out of 3M). When 99 negatives are sampled randomly, the probability of drawing a non-Cleora item is very high. A negative that is outside the Cleora set gets score -2.0 — it is trivially easy to rank the positive above it.

The canonical evaluation uses a fixed seed=42, which happened to sample a specific distribution of negatives. The ablation was run without a fixed seed. This is why the canonical result (seed=42) is stated as the authoritative figure.

The lesson: when a model assigns a hard out-of-domain score, the specific negative draw matters more than usual. Always fix evaluation seeds.
16
Why choose RRF over learned fusion weights for combining BM25 and semantic results?
Evaluation
▼
Answer

RRF is parameter-free: the formula 1 / (k + rank) with k=60 requires no training data and produces stable fusion across query distributions.

Learning fusion weights requires labelled (query, relevant-item) pairs, which would introduce dependency on a manually curated evaluation set that may not generalise to the full query distribution (Vietnamese queries, image queries, long-tail books). RRF's robustness to weight tuning makes it the right choice when the query distribution is heterogeneous.

The implementation also applies adaptive weighting: the BM25 channel weight scales with Tantivy's score normalisation, and the semantic weight adjusts inversely — a lightweight data-driven adjustment without full training.

17
Your HNSW recall is only 0.521 — aren't you losing half your nearest neighbours?
Weaknesses
▼
Answer

Recall@k measures what fraction of exact top-k neighbours the HNSW index returns. A recall of 0.521 means approximately half of the true nearest neighbours are in the approximate result set. Two mitigations are in place:

1. Tantivy BM25 compensation. The BM25 stage adds lexical-match candidates that the approximate semantic search misses — items matching exact title or author tokens appear via BM25 even if they were not in the HNSW beam.

2. HR@10 robustness. HR@10 only requires the ground-truth item to appear somewhere in the top-10 re-ranked list. The BM25 fusion partially restores candidates missed by HNSW.

The 5.1× latency reduction (612 ms → 120 ms P50) justifies this approximation for interactive search. The flat index is retained for evaluation and exact vector reconstruction.

Cleora covers only 12.5% of the catalogue (375k/3M). What happens for long-tail items?
Weaknesses
▼
Answer

Long-tail items with no co-purchase history are invisible to Pipeline A. They can still surface in Pipeline B (DIF-SASRec + HNSW semantic search) if their BGE-M3 embedding is close to the user's profile vector. However, 2,641 test users (2.6%) received no recommendation from either pipeline.

The practical mitigation is to expand the Cleora graph to the full catalogue as interaction data accumulates. The incremental hot-swap pipeline already supports this without a server restart — a batch re-embedding of the full catalogue with accumulated interaction data is the next step.

This is acknowledged as a limitation in Section 7.5 alongside the adaptive content veto threshold as the two highest-priority future improvements.

The /interact click endpoint has P50=320ms. Isn't that too slow for a responsive UI?
Weaknesses
▼
Answer

The 320 ms includes the DIF-SASRec gradient step and checkpoint serialisation to disk — a background update from the user's perspective. The frontend fires the click event as a non-blocking fetch without awaiting the response.

The UI feedback (Interested checkmark, profile update) is rendered optimistically immediately. The 320 ms response arrives and confirms the server-side update, but the user's perceived latency for the click action is ~0 ms.

The stated future improvement is to move the gradient step off the synchronous request path entirely into a background task queue, which would bring P50 to under 10 ms for the interaction endpoint.

What happens when a new user provides false interactions to manipulate recommendations?
Weaknesses
▼
Answer

The system is designed for authenticated users in a controlled deployment scope, so there is no strong adversarial pressure in the current context. However, the content veto (τ = 0.3) provides a structural constraint: DIF-SASRec can only recommend items semantically close to the user's BGE-M3 profile mean.

A user injecting random click events would shift their profile mean toward an incoherent vector, causing more candidates to be filtered by the veto — making the manipulation self-limiting. This is not a formal robustness guarantee, but it is a practical defence for the academic use case.

A more robust solution would involve anomaly detection on the click sequence (e.g., detecting a sudden jump in category distribution), which is listed as a direction for future work.

How Each Method Handles the Benchmark

1. Random Baseline
Assigns a uniform random score to each of the N+1 candidates and picks the top-10 by chance. Under N=99 this yields HR@10 = 0.100 by construction (1 correct item in 100 → 10% chance it lands in top-10 at random). This is the lower bound every method must beat. Results: HR@10 = 0.100 · NDCG@10 = 0.045.

2. Content Baseline (BGE-M3 profile mean-pool)
Takes the user's entire training sequence, looks up the pre-computed BGE-M3 1024-d embedding for each clicked item, and computes a mean-pool profile vector. At evaluation time, the cosine similarity between this profile vector and each candidate's BGE-M3 embedding is computed; candidates are ranked by that score. No sequential modelling, no graph signal — pure semantic overlap. This is the "what if we just average the user's taste?" baseline. Results: HR@10 = 0.4346 · NDCG@10 = 0.302 · MRR@10 = 0.261.

3. GRU-SeqDQN (prior system)
A GRU encodes the click sequence into a fixed hidden state, and a Deep Q-Network assigns a Q-value to each item in the catalogue. At evaluation time, the model scores all N+1 candidates with the Q-network and picks the top-10. Two failure modes explain why it scores below random:
(a) The GRU bottleneck compresses hundreds of interactions into one vector — positional context is lost.
(b) The DQN must generalise Q-values over 3M items; at this scale the action space is too large to converge. Results: HR@10 = 0.1031 · NDCG@10 = 0.047 — statistically indistinguishable from random.

4. DIF-SASRec / Pipeline B
At evaluation, the user's most recent 50 interactions (padded if shorter) are fed as a sequence of (BGE-M3 embedding, category ID) pairs into the transformer. The model runs a forward pass through 4 causal self-attention blocks, producing an intent vector from the last position. Each of the N+1 candidates is then scored by dot product between its BGE-M3 embedding and the intent vector; candidates are ranked by this score. The content veto (τ = 0.3) is not applied during evaluation — all N+1 candidates are scored directly. Results: HR@10 = 0.7745 · NDCG@10 = 0.502 · MRR@10 = 0.419.

5. Pipeline A (Cleora + BGE-M3)
This pipeline does not use a neural sequence model at evaluation. Instead:
(i) The user's Cleora-space embeddings (one per clicked item) are mean-pooled into a behavioural profile vector.
(ii) The Cleora FAISS flat-IP index is queried to find nearest co-purchase neighbours.
(iii) Candidates are re-ranked by cosine similarity to the user's BGE-M3 mean-pool profile.
Crucially, any candidate whose ASIN is not in the Cleora index is assigned a hard score of -2.0 and ranked last. This means the N+1 candidates include both in-Cleora and out-of-Cleora items — if the ground-truth item is in the Cleora set and the 99 sampled negatives happen to be outside it, Pipeline A trivially wins. This is the source of the seed-sensitivity described in the ablation note. Results: HR@10 = 0.9047 · NDCG@10 = 0.539 · MRR@10 = 0.430.
