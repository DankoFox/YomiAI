\subsection{Text Encoder Upgrade: BLaIR to BGE-M3}
\label{sec:encoder_upgrade}

The BLaIR encoder is replaced by \texttt{BAAI/bge-m3}~\cite{chen2024bge}, a multilingual model producing 1{,}024-dimensional embeddings.
BGE-M3 is the single source of truth for all text embeddings in the system: user profile vectors, item embeddings in the FAISS text index, and query encodings at search time all use the same model, keeping the retrieval pipeline consistent.
The \texttt{TEXT\_EMBED\_DIM} constant in \texttt{app/config.py} is the sole location that needs updating if a future encoder is adopted.

\subsection{NLLB-200 Multilingual Translation Pipeline}
\label{sec:nllb_pipeline}

A three-stage translation pipeline is inserted before the BGE-M3 encoding step in the search route (Figure~\ref{fig:translation_pipeline}).

\begin{figure}[H]
\centering
\includegraphics[width=0.55\textwidth]{images/chapter4/fig_translation_pipeline}
\caption{NLLB-200 translation pipeline. Language detection (lingua, $< 1$\,ms), greedy translation, and a quality gate that retries with beam search if the first pass leaves source-language tokens in the output.}
\label{fig:translation_pipeline}
\end{figure}

\begin{enumerate}
    \item Language detection: The \texttt{lingua} library identifies the input language in under 1\,ms. If the detected language is English, the translation step is skipped entirely.
    \item NLLB-200 translation: For the 19 supported non-English languages, the \texttt{facebook/nllb-200-distilled-600M} model translates the query to English. A fast greedy pass (\texttt{num\_beams=1}) is executed first.
    \item Quality gate: A heuristic checks whether any source-language words survived into the translation output, a reliable indicator of partial decoding failure. If untranslated tokens are detected, the query is retried with \texttt{num\_beams=4}, trading \textasciitilde{}30 ms for a cleaner translation.
    \item LRU caching: Translated queries are cached via \texttt{@lru\_cache(maxsize=2048)}, so repeated queries (e.g., common search terms) cost 0 ms after the first miss.
\end{enumerate}

Both the NLLB model and the lingua detector are lazy-loaded on first use and eagerly warmed up at server startup to eliminate the cold-start P95 latency spike.

\subsection{Search Pipeline Parallelisation}
\label{sec:parallel_search}

In the prior system, text encoding and CLIP image encoding were executed sequentially.
The revised search route runs them concurrently using an \texttt{anyio} task group:

\begin{itemize}
    \item \texttt{encode\_text\_task}: runs \texttt{ml.encode\_text(query, text\_encoder)} in a background thread.
    \item \texttt{encode\_image\_task}: runs \texttt{ml.encode\_image\_b64(..., clip\_model)} in a parallel thread.
\end{itemize}

Both tasks are submitted to the task group simultaneously; the route waits only for the slower of the two before proceeding to the FAISS and Tantivy retrieval stages, which are fused via adaptive weighted RRF (BM25 channel weight scales with query confidence; semantic weight adjusts inversely).
For text-only queries, the CLIP task is skipped.
The combined effect of the encoder upgrade, HNSW index, and parallelisation reduces end-to-end warm-cache search latency from 1{,}102 ms to 59 ms (Table~\ref{tab:latency_stages}).

\subsection{Dual-Mode Recommendation Architecture}
\label{sec:dual_mode_rec}

The recommendation backend uses two independent pipelines: Pipeline~A (People Also Buy) and Pipeline~B (You Might Like).
Both return their top 10 items and are displayed side by side in a two-column panel.
Figure~\ref{fig:rec_funnel} illustrates the recommendation funnel.

\begin{figure}[H]
\centering
\includegraphics[width=0.90\textwidth]{images/chapter4/fig_rec_funnel}
\caption{Dual-mode recommendation funnel. Pipeline~A (behavioural) and Pipeline~B (sequential) run independently and each return top 10 items, displayed side by side in the interface. Cold-start users (fewer than 5 interactions) receive items sampled from the Cleora catalogue.}
\label{fig:rec_funnel}
\end{figure}

\paragraph{Pipeline A: Cleora + BGE-M3 (People Also Buy).}
Candidate generation uses two complementary Cleora lookups.
First, a mean-pool of the user's Cleora-space item embeddings forms a behavioural profile vector, which is used to query the Cleora co-purchase index (375{,}439 items) for up to 50 nearest neighbours.
Second, per-item Cleora neighbours are retrieved for each of the user's 5 most recent interactions, adding locally relevant co-purchase candidates.
The union of both sets is then filtered by a content veto: candidates whose cosine similarity to the user's BGE-M3 profile vector falls below $\tau = 0.3$ are discarded.
Surviving candidates are ranked by BGE-M3 semantic similarity to the profile vector, and the top items are returned.
(The BGE-M3 profile used here for veto and re-ranking is a separate mean-pool of BGE-M3 text embeddings, distinct from the Cleora-space profile used for the initial index query.)

\paragraph{Pipeline B: DIF-SASRec (You Might Like).}
An \texttt{AgentPool} of 8 isolated DIF-SASRec agents handles concurrent personalisation requests.
For each request, the user's BGE-M3 profile vector is used to retrieve 200 candidate items from the HNSW index.
Those candidates pass through the same content veto filter ($\tau = 0.3$) as Pipeline~A.
The surviving candidates are then scored by DIF-SASRec: an agent loads the user's personal checkpoint, runs a forward pass over the recent click sequence to produce an intent vector, and ranks candidates by dot product against that vector.
Per-user fine-tuning is triggered at every click event, updating the personal checkpoint via a sampled softmax gradient step.

\paragraph{Cold-start handling.}
Users with fewer than \texttt{COLD\_START\_THRESHOLD} = 5 interactions bypass both pipelines.
The fallback samples items uniformly from the intersection of the Cleora ASIN set and the FAISS index, providing a diverse starting point until enough signal accumulates.
