\section{Search and Retrieval}
\label{sec:app_retrieval}

\subsection{API Contract}

Search is exposed via a single endpoint, \texttt{POST /search}, which accepts a JSON body with three optional fields:

\begin{itemize}
    \item \texttt{query} (string, default \texttt{""}): the text query, in any of the 19 supported languages.
    \item \texttt{image\_base64} (string, optional): a base64-encoded image for CLIP visual search.
    \item \texttt{top\_k} (integer, default 20): number of results to return.
\end{itemize}

The response is a JSON object containing a \texttt{results} array of hydrated item records (ASIN, title, author, genre, description, cover URL, relevance score, and per-modality similarity scores when applicable), a \texttt{total} count, a \texttt{live\_encoding} flag, and the echoed \texttt{query} string.
An optional \texttt{debug=true} query parameter appends a \texttt{\_debug\_timings} dictionary to the response, reporting per-stage latency in milliseconds (translation, text encoding, CLIP encoding, FAISS search, BM25 re-ranking, metadata hydration, and total).

\subsection{Retrieval Pipeline}

The internal pipeline executed by the \texttt{POST /search} handler is:

\begin{enumerate}
    \item Language detection and translation: the \texttt{lingua} detector identifies the input language in under 1\,ms. Non-English queries are translated to English by the NLLB-200 pipeline (Section~\ref{sec:nllb_pipeline}).
    \item Parallel encoding: text and image are encoded concurrently via an \texttt{anyio} task group. Each encoder runs in a background thread to avoid blocking the async event loop.
    \item FAISS HNSW search: the text vector is queried against \nolinkurl{bge_index_hnsw.faiss}; the image vector (if present) is queried against the CLIP HNSW index. Both retrieve 50 candidates.
    \item Tantivy BM25 re-ranking: the original query string is searched against the Tantivy full-text index to retrieve a ranked keyword hit list.
    \item RRF fusion: the HNSW and BM25 candidate lists are fused by Reciprocal Rank Fusion~\cite{cormack2009rrf} to produce a single ranked list.
    \item Metadata hydration: each ASIN in the final list is resolved against the in-memory DataFrame to attach display metadata.
\end{enumerate}

\subsection{Profile-Based Retrieval}

The \texttt{GET /recommend} endpoint uses a separate retrieval path.
For authenticated warm users, the profile manager maintains two profile vectors: a Cleora co-purchase embedding (mean of clicked items' Cleora vectors) and a BGE-M3 text embedding (weighted mean of clicked items' BGE-M3 vectors).
Pipeline~A queries the Cleora FAISS index (\texttt{IndexFlatIP}) with the user's Cleora profile vector to retrieve up to 50 co-purchase neighbours; it also fetches per-seed-item Cleora neighbours for the five most recent interactions.
The combined candidate pool is then re-ranked by cosine similarity to the user's BGE-M3 profile vector (content veto threshold $\tau = 0.3$), and the top items are returned as People Also Buy results.
Pipeline~B queries the BGE-M3 HNSW index directly with the user's BGE-M3 profile vector, applies the same content veto filter, then scores surviving candidates with the DIF-SASRec sequential model before returning the You Might Like results.
